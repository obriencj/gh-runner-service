# `gh-runner` — Addendum A: Resource Control

Extension to the base design specification. Covers CPU, memory, and task limits
for job containers and for the runner containers themselves.

Status: draft
Depends on: base spec §§5–10, as built in 1.0.0

---

## 0. Assumed baseline

This addendum takes the following as established and working:

- Ephemeral runner containers under Quadlet, one job per container lifetime.
- The `docker` → `podman` shim inside the runner image, already rewriting argv
  on every `create`.
- Job containers created by **host** Podman as siblings of the runner
  container, via the mounted socket.
- `instances.d/<id>.conf` as the sole configuration store, with
  `gh-runner-ctl sync` reconciling derived artifacts from it.
- `RUNNER_ID` present in the runner container's environment.

---

## 1. Problem statement

Limits applied to a runner container do not constrain its jobs.

Because job containers are siblings rather than children, they are placed in
their own cgroups by host Podman. A `MemoryMax=` on `gh-runner@01.container`
bounds `Runner.Listener` and `Runner.Worker` — a few hundred MB of .NET — and
has no bearing on the compiler that consumes the machine.

Resource control therefore has to be applied where the job containers actually
land, and it has to be expressible in `instances.d/<id>.conf` like everything
else.

---

## 2. Design: per-instance slices

Job containers are placed into a dedicated systemd slice per instance. The shim
injects the parent; the numbers live in the slice unit.

```
user@<uid>.service
├── app.slice
│   └── gh-runner@01.service          runner container (Quadlet-generated)
│                                     RUNNER_MEMORY_MAX, RUNNER_PIDS_LIMIT
└── ghr.slice                         aggregate envelope for all CI work
    ├── ghr-01.slice                  job containers for instance 01
    ├── ghr-02.slice
    └── ghr-NN.slice
```

The shim appends to every `create`:

```
--cgroup-parent=ghr-${RUNNER_ID}.slice
```

`RUNNER_ID` is already in the container environment, so this needs no config
lookup and no regeneration when limits change.

### Slice naming

**Dashes in slice names denote hierarchy.** `a-b-c.slice` is nested under
`a-b.slice` under `a.slice`, and systemd creates the implicit parents. Naming
the children `gh-runner-01.slice` would therefore materialise a stray
`gh.slice` in the tree — harmless but confusing in `systemd-cgtop`, and it
makes `gh-runner.slice` look like the aggregate when it is really a middle
layer.

`ghr-<id>.slice` under `ghr.slice` gives a clean two-level hierarchy with no
artifacts. The prefix is deliberately not a word.

### The aggregate slice earns its place

`ghr.slice` is not decoration. cgroup v2 enforces that a child's `AllowedCPUs`
is intersected with its parent's effective set, so `ghr.slice` reserves the
cores available to CI at all and the per-instance slices partition that
reservation:

```ini
# /etc/systemd/user/ghr.slice
[Slice]
AllowedCPUs=0-27
MemoryMax=96G
MemorySwapMax=0
```

Cores 28–31 are then structurally unavailable to any job, and stay responsive
for sshd, the user manager, and Podman itself under full load. A single global
`MemoryMax` also caps total CI memory regardless of how the per-instance
budgets are set, so an operator cannot oversubscribe the box by editing four
files independently.

### Runner containers stay outside `ghr.slice`

Deliberate. `JOB_MEMORY_MAX` should mean "memory available to the build", not
"build plus .NET runtime overhead". Keeping the runner container in its
Quadlet-generated unit under `app.slice` keeps the job budget clean and makes
`systemd-cgtop ghr.slice` a direct read of CI consumption.

## 3. Configuration surface

Keys are prefixed by destination. One file, three targets.

```ini
# /etc/gh-runner/instances.d/01.conf

# --- runtime env → entrypoint.sh, via EnvironmentFile
RUNNER_URL=https://github.com/koskari-lang/koskari
RUNNER_LABELS=alma10,podman,c

# --- job envelope → ghr-01.slice
JOB_CPUS=0-6
JOB_MEMORY_MAX=24G
JOB_TASKS_MAX=4096

# --- job podman flags → read by the shim from container env
JOB_SHM_SIZE=1g
JOB_PIDS_LIMIT=2048

# --- runner container canary → gh-runner@01.container.d/limits.conf
RUNNER_MEMORY_MAX=2G
RUNNER_PIDS_LIMIT=512
```

| Prefix | Destination | Generated by `sync` | Applies |
|---|---|---|---|
| `RUNNER_URL`, `RUNNER_LABELS`, … | container env | no — `EnvironmentFile` | next job |
| `JOB_CPUS`, `JOB_MEMORY_MAX`, `JOB_TASKS_MAX` | `ghr-<id>.slice` | yes | **live** |
| `JOB_SHM_SIZE`, `JOB_PIDS_LIMIT` | shim argv | no — container env | next job |
| `RUNNER_MEMORY_MAX`, `RUNNER_PIDS_LIMIT` | `.container.d/limits.conf` | yes | next job |

The `JOB_SHM_SIZE` row is the pattern to prefer where possible: anything the
shim can read as an environment variable costs `sync` nothing and needs no
generated artifact.

---

## 4. Apply semantics

Three distinct behaviours, and `ctl show` annotates each key with which one it
has:

**Live.** Slice properties. `systemctl --user daemon-reload` re-applies resource
control settings to already-active units, so raising `JOB_MEMORY_MAX` retunes
the cgroup without disturbing a running job. `sync` performs the reload.

**Next job.** Container env and Quadlet-fixed values. Quadlet resolves these at
container creation, so they take effect when the current container exits at its
job boundary and the ephemeral loop starts a fresh one. No forced restart
required or wanted.

**Immediate, destructive.** `ctl <verb> --now` restarts the container and kills
any running job. Never the default.

This sharpens the graceful/`--now` distinction from base spec §7: slice changes
are always safe and immediate; everything else waits for a boundary.

---

## 5. CPU allocation policy

### `JOB_CPUS` is a cpuset, not a bandwidth quota

`AllowedCPUs=` (equivalently `--cpuset-cpus`) constrains `sched_getaffinity`,
so `nproc` inside a job container reports the pinned count. `make -j$(nproc)`,
Cargo, Go, and modern JVMs all size themselves correctly with no workflow
changes.

A bandwidth quota (`CPUQuota=`, `--cpus`) does not: the container still observes
32 CPUs, spawns 32 compilers, and thrashes against a fraction of a machine.
Measurably worse than no limit at all for compile-heavy work.

`JOB_CPUS` is consequently the build-sizing knob, and workflows should not
hardcode `-j`.

### Allocation is explicit and disjoint

`sync` does **not** divide cores among enabled instances. Automatic
redistribution would silently reshuffle the pinning of running instances the
moment a new one is enabled.

- `ctl add --auto-cpus` proposes the next free contiguous range at scaffold
  time, writes it into the conf, and does not revisit it.
- `ctl doctor` lints the resulting allocation: overlapping sets between enabled
  instances, sets exceeding `ghr.slice`'s `AllowedCPUs`, and cores inside the
  CI reservation claimed by no instance.
- `ctl enable` refuses on overlap unless `--force`.

Disjoint sets trade peak utilisation for predictable build times. On a host
that is idle much of the day, predictability is worth more, and it keeps `nproc`
honest — which overlapping sets plus `CPUWeight` would not.

## 6. `gh-runner-ctl` changes

**`sync`** additionally:
1. Writes `/etc/systemd/user/ghr.slice` from `gh-runner.conf` globals.
2. Writes `/etc/systemd/user/ghr-<id>.slice` per enabled instance.
3. Writes `.container.d/limits.conf` per instance from `RUNNER_*` keys.
4. Removes slices and drop-ins for instances no longer configured.
5. `systemctl --user daemon-reload`.

All five are derived state regenerated from `instances.d/`. The single-store
invariant is unchanged.

**`show`** gains a destination and apply-semantics column per key.

**`doctor`** gains:

```bash
# cpuset delegated to the user manager — silently no-ops if absent
cat /sys/fs/cgroup/user.slice/user-$UID.slice/user@$UID.service/cgroup.controllers

# effective set after intersection with parent
cat /sys/fs/cgroup/.../ghr.slice/ghr-01.slice/cpuset.cpus.effective

# end-to-end: a live job container is actually parented here
systemd-cgls --user-unit ghr-01.slice
```

The third is the one that matters. If `--cgroup-parent` is not honoured, job
containers land in the default scope and every limit in this addendum is
decorative while appearing correctly configured.

**`doctor --live`** runs the third check against a synthetic job and is the
recommended post-install verification.

## 7. Defaults

Shipped in `/etc/gh-runner/gh-runner.conf`, overridable per instance:

```ini
GHR_CPUS=0-27                  # ghr.slice reservation; leaves 28-31 to the host
GHR_MEMORY_MAX=96G
JOB_TASKS_MAX=4096
JOB_SHM_SIZE=1g                # 64MB default breaks anything Chromium-based
JOB_PIDS_LIMIT=2048
RUNNER_MEMORY_MAX=2G           # canary, not a budget
RUNNER_PIDS_LIMIT=512
```

`MemorySwapMax=0` is set unconditionally on `ghr.slice`. Swapping a build is
slower than failing it, and an OOM kill inside a job container surfaces as exit
137 — a clear, attributable failure rather than an hour of thrash.

## 8. Deliberate exclusions

| Excluded | Reason |
|---|---|
| I/O limits (`IOReadBandwidthMax=` etc.) | Device-scoped, and meaningless through the ZFS zvol layering underneath. Revisit only if a specific workload demands it. |
| Automatic core redistribution on enable/disable | Silently repins running instances. See §5. |
| Per-workflow limit overrides | Would let repository content set its own resource envelope. The envelope is an operator concern. |
| `CPUQuota=` as an alternative to cpuset | Actively harmful for compile workloads. See §5. |
